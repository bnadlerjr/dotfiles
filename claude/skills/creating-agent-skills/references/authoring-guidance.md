## Start from real expertise

The most common way skills fail is being generated by an LLM from general training
knowledge with no domain context. The result is vague and generic — "handle errors
appropriately", "follow authentication best practices" — instead of the specific API
patterns, edge cases, and project conventions that make a skill worth loading.

**Extract from a hands-on task.** Do the real work in conversation first, then extract
the reusable pattern. Pay attention to:

- Steps that worked — the sequence that led to success
- **Corrections you made** — where you steered the agent ("use X not Y", "check for Z")
- Input/output formats — what the data actually looked like
- Context you supplied — project facts the agent could not have known

**Synthesize from project artifacts.** Feed real material in: internal runbooks and
style guides, API specs and schemas, code review comments, version control history
(especially fixes — they reveal patterns through what actually changed), and real
failure cases with their resolutions.

A data-pipeline skill built from your team's actual incident reports will outperform
one built from a generic "data engineering best practices" article, because it captures
*your* schemas, failure modes, and recovery procedures.

**Refine with real execution.** Run the skill against real tasks and feed the results
back — all of them, not just failures. Ask: what triggered false positives? What was
missed? What could be cut? Even a single execute-then-revise pass noticeably improves
quality.

Read execution traces, not just final outputs. If the agent wastes time, the usual
causes are instructions too vague (it tries several approaches first), instructions
that don't apply to the current task (it follows them anyway), or too many options with
no clear default.

## Spending context wisely

Once a skill activates, its whole body loads alongside conversation history, system
context, and other active skills. Every token competes for attention.

### Add what the agent lacks, omit what it knows

Focus on what the agent *wouldn't* know: project conventions, domain procedures,
non-obvious edge cases, the particular tools to use. Don't explain what a PDF is, how
HTTP works, or what a migration does.

Too verbose — the agent already knows what PDFs are:

````markdown
## Extract PDF text

PDF (Portable Document Format) files are a common file format that contains text,
images, and other content. To extract text from a PDF, you'll need to use a library.
pdfplumber is recommended because it handles most cases well.
````

Better — straight to what the agent wouldn't know:

`````markdown
## Extract PDF text

Use pdfplumber for text extraction. For scanned documents, fall back to pdf2image
with pytesseract.

```python
import pdfplumber

with pdfplumber.open("file.pdf") as pdf:
    text = pdf.pages[0].extract_text()
```
`````

Ask of every piece of content: **"Would the agent get this wrong without this
instruction?"** If no, cut it. If unsure, test it. If the agent already handles the
whole task well without the skill, the skill may not be adding value at all — see
[evaluating-skills.md](evaluating-skills.md).

### Design coherent units

Scoping a skill is like scoping a function: it should encapsulate a coherent unit of
work that composes with other skills.

- **Too narrow** — several skills must load for one task, risking overhead and
  conflicting instructions.
- **Too broad** — hard to activate precisely.

Querying a database and formatting the results may be one coherent unit. Adding
database administration to it is trying to do too much.

### Aim for moderate detail

Overly comprehensive skills hurt: the agent struggles to extract what's relevant and
may chase unproductive paths triggered by instructions that don't apply. Concise,
stepwise guidance with a working example beats exhaustive documentation. When you find
yourself covering every edge case, ask whether most are better left to the agent's
judgment.

### Structure large skills with progressive disclosure

Keep `SKILL.md` under 500 lines and 5,000 tokens — just the core instructions needed
on every run. Move detail into `references/`.

The key is telling the agent **when** to load each file. "Read
`references/api-errors.md` if the API returns a non-200 status code" is far more
useful than "see references/ for details." See [skill-structure.md](skill-structure.md).

## Calibrating control

Match the specificity of an instruction to the fragility of the task. Most skills
mix all three levels — calibrate each part independently.

### High freedom

When multiple approaches are valid and the task tolerates variation. Explaining *why*
beats rigid directives; an agent that understands the purpose makes better
context-dependent decisions.

```markdown
## Code review process

1. Check all database queries for SQL injection (use parameterized queries)
2. Verify authentication checks on every endpoint
3. Look for race conditions in concurrent code paths
4. Confirm error messages don't leak internal details
```

### Medium freedom

When a preferred pattern exists but variation is acceptable — a template that can be
adapted, a default that configuration may override.

### Low freedom

When operations are fragile, consistency is critical, or a sequence must be followed
exactly.

````markdown
## Database migration

Run exactly this sequence:

```bash
python scripts/migrate.py --verify --backup
```

Do not modify the command or add additional flags.
````

Mismatches cause real damage: too much freedom on fragile tasks produces failures; too
little on creative tasks produces rigid, suboptimal output.

### Provide defaults, not menus

When several tools could work, pick one and mention alternatives briefly.

Too many options — the agent must research and compare before starting:

```markdown
You can use pypdf, pdfplumber, PyMuPDF, pdf2image, pdfminer, or tabula-py.
Choose based on your needs.
```

Clear default with an escape hatch:

```markdown
Use pdfplumber for text extraction.
For scanned PDFs requiring OCR, use pdf2image with pytesseract instead.
```

### Favor procedures over declarations

A skill should teach how to approach a *class* of problems, not what to produce for one
instance.

Specific answer — useful only for this exact task:

```markdown
Join the `orders` table to `customers` on `customer_id`, filter where
`region = 'EMEA'`, and sum the `amount` column.
```

Reusable method — works for any analytical query:

```markdown
1. Read the schema from `references/schema.yaml` to find relevant tables
2. Join tables using the `_id` foreign key convention
3. Apply any filters from the user's request as WHERE clauses
4. Aggregate numeric columns and format as a markdown table
```

Specific details still belong in skills — output templates, constraints like "never
output PII", tool-specific instructions. The point is that the *approach* generalizes.

## Being clear and direct

**The golden rule:** show your skill to someone with minimal context and ask them to
follow it. If they're confused, the agent will be too.

### Be specific

| Vague | Specific |
|---|---|
| "Help with the report" | "Generate a markdown report with three sections: Executive Summary, Key Findings, Recommendations" |
| "Process the data" | "Extract customer names and emails from the CSV, remove duplicates, save as JSON" |
| "Clean the data" | "Remove rows with empty name/email/date, standardize dates to YYYY-MM-DD, dedupe on email" |

### Eliminate ambiguous obligation

| Avoid | Use |
|---|---|
| "Try to…" (optional?) | "Always…" / "Never…" |
| "Should probably…" | "Must…" / "May optionally…" |
| "Generally…" (when are exceptions allowed?) | "Always… except when…" |
| "Consider…" | "If X, then Y" |

### Define edge cases

Don't leave the agent guessing. "Extract email addresses and save to a JSON array"
leaves four questions unanswered. Answer them:

```markdown
- No emails found: save an empty array `[]`
- Duplicates: keep only unique addresses
- Malformed addresses: skip, and log to stderr
- Output: an array of strings, one address per element
```

### Show, don't just tell

When format matters, an example communicates what prose cannot — exact spacing,
capitalization, tone, level of detail, and the pattern across cases. See the examples
pattern in [instruction-patterns.md](instruction-patterns.md).

### Give decision criteria

When the agent must choose, say what governs the choice:

```markdown
Use a bar chart when comparing quantities across fewer than 10 categories and
exact values matter. Use a line chart for trends over continuous time. Use a
scatter plot when showing the relationship between two variables.
```

### Separate must from nice-to-have from must-not

"The report should include financial data, customer metrics, and market analysis. It
would be good to have visualizations. Don't make it too long." — are all three
required? Are charts optional? How long is too long?

```markdown
**Required**: financial data, customer metrics, market analysis; maximum 5 pages
**Optional**: charts, industry benchmarks, projections
**Never**: confidential customer names, undefined jargon
```

### Provide context and success criteria

State what the output is for, who reads it, and what "done" means. "Process the CSV and
generate a report" gives the agent no way to know when it has succeeded.

## Writing descriptions

The `description` carries the entire burden of triggering. At startup the agent loads
only `name` and `description`; if the description doesn't convey when the skill is
useful, it never activates.

- **Write in third person.** The description is injected into the system prompt.
  Not "I can help you process Excel files" or "You can use this to…".
- **Frame the trigger as an instruction.** "Use when the user…" tells the agent when
  to act.
- **Cover intent, not mechanics.** The agent matches against what the user asked for.
- **Be pushy.** List contexts explicitly, including where the user won't name the
  domain: "even if they don't explicitly mention 'CSV' or 'analysis'."
- **Stay under 1024 characters.** Hard limit. Descriptions grow during optimization —
  re-check.

Good:

```yaml
description: Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.
```

Poor:

```yaml
description: Helps with documents
```

One nuance: agents typically consult skills only for tasks needing capability beyond
what they already have. "Read this PDF" may not trigger a PDF skill however well the
description matches, because basic tools suffice. Descriptions earn their keep on
specialized knowledge, unfamiliar APIs, and domain workflows.

To test triggering systematically, see [evaluating-skills.md](evaluating-skills.md).

## Content hygiene

### Use consistent terminology

Pick one term and keep it. Mixing "API endpoint" / "URL" / "API route" / "path", or
"field" / "box" / "element" / "control", forces the agent to work out whether they mean
the same thing.

### Avoid time-sensitive information

Don't write "If you're doing this before August 2025, use the old API." Structure it
instead:

````markdown
## Current method

Use the v2 endpoint: `api.example.com/v2/messages`

## Old patterns

<details>
<summary>Legacy v1 API (deprecated 2025-08)</summary>
The v1 API used: `api.example.com/v1/messages`
</details>
````

The same applies to hardcoded years in search strings and example commands — they
silently rot.

### Use forward slashes

`scripts/helper.py`, never `scripts\helper.py`.

## Testing across models

A skill is an addition to a model, so its effectiveness depends on the model. Aim for
instructions that work across the ones you actually use:

- **Smaller/faster models** benefit from explicit instructions, complete examples, and
  step-by-step workflows.
- **Larger reasoning models** benefit from concise instructions, principles over
  procedures, and higher degrees of freedom — they suffer from over-explanation.

A working example plus a one-line escape hatch tends to serve both. Start at medium
detail, test, and adjust from observed behaviour rather than assumption.
